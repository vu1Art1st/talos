# Talos 演进路线（ROADMAP）

> 基线：2.20.3（2026-09-26）
>
> 本文件是 Talos 功能演进、技术治理与风险收敛的唯一入库规划真相源。已完成事项应同步写入
> `docs/RELEASE.md` 后移入本文档末部的「已完成归档」；已取消或明确不排期的事项保留在「已取消 /
> 暂缓」中，避免后续重复讨论。新增条目必须声明范围、依赖、验收标准和对现有统计口径、
> 工单状态机、报告复测口径、数据库迁移的影响。

## 一、规划原则与当前结论

### 1.1 规划原则

1. **先正确，再扩展**：数据正确性、并发一致性、任务可恢复性优先于新增业务页面。
2. **复用现有单源**：继续统一使用 `app/core/filters.py`、`plan_query`、`plan_service`、
   `report_meta`、`/meta` 字典、前端 `client.ts` 与既有 composables，禁止新造平行实现。
3. **业务改动必须可审计、可迁移、可回滚**：涉及模型变更时同步 Alembic 迁移、
   `DEPRECATED_COLUMNS`、备份与恢复验证、`docs/RELEASE.md`。
4. **不承诺具体日期**：按 P0 → P1 → P2 顺序推进，每项达到验收标准后再发布。
5. **保持既定决策**：不引入 CI，不引入 SQLite，不恢复已取消的扫描器接入与定期报表订阅；
   只有触发条件明确成立时才重新评估。

### 1.2 下一阶段结论

当前 Talos 已跨过「主要功能是否可用」阶段，进入「高频业务是否长期可靠、可运营、可扩展」阶段。
下一阶段不应以页面数量为目标，建议按以下顺序推进：

1. **P0：可靠性加固**：修复已识别的日期筛选隐患、并发写入竞态、后台任务卡死和数据量增长后的
   查询退化；补齐报告防丢稿和基础可观测性。
2. **P1：业务闭环增强**：落地 SLA 修复时限、个人待办工作台、站内通知中心、通知投递可追踪、
   报告模板中心与开放 API 成熟化。
3. **P2：规模化与平台化**：部门级数据权限、全文检索、资产测绘联动、漏洞验证插件、
   性能与灾备演练。

## 二、现状基线

### 2.1 架构与代码组织

| 层 | 现状 |
|---|---|
| 接入层 | FastAPI，统一 `/api/v1` 前缀；OpenAPI 当前约 115 个路径、158 个操作；PAT 与 JWT 分工明确 |
| 后端核心 | `app/core` 承载配置、认证、分页、筛选、限流、文件安全、出站安全、时间与 Excel 工具 |
| 领域层 | `app/models`、`app/schemas`、`app/services` 按资产 / 漏洞 / 报告 / 导入 / 专项 / 系统分域 |
| 数据层 | PostgreSQL 16 单栈；SQLAlchemy 2.0 async；Alembic 是唯一 schema 演进路径 |
| 异步层 | arq + Redis；Redis 不可用时 API 可降级为进程内任务；2.20.3 起补齐租约 / 心跳 / 重试退避 / 死信与启动回收（`services/task_lifecycle.py`） |

| 文档处理 | python-docx 解析、docxtpl/htmldocx 生成、Gotenberg 转 PDF；导入与导出共用 `report_meta` |
| 部署 | Docker Compose：api / worker / frontend / postgres / redis / gotenberg；备份、恢复、升级均有脚本 |

**组织评价**：分层边界清晰，跨模块共享实现已经大量下沉到 services、core 和 composables。当前主要
问题不是缺少架构层次，而是若干跨接口口径仍需继续收敛，异步任务和并发写入缺少数据库层面的
最终保障。

### P0-1 统一 DateTime 条件的时间区间语义 ✅（2.20.3）

**问题**

- `app/core/filters.py::build_filter_expr` 对 DateTime 字段仍使用 `func.date(col)` 与日期字符串比较。
- 已用 PostgreSQL 方言只读编译复核：生成 SQL 为 `date(testing_plans.create_time) >= %(date_1)s`，
  绑定类型为 `String`。这违反 `AGENTS.md` 中「DateTime 列禁止与日期字符串比较」的硬性口径，
  在 PostgreSQL + asyncpg 下存在 `date >= character varying` 报错风险。
- `plan_query` 的统计周期已使用正确的半开区间，但通用聚合筛选没有复用该口径。

**实施项**

- [ ] 在通用筛选引擎中区分「DateTime 字段的日期区间」与「普通日期字符串字段」。
- [ ] DateTime 字段统一按 `[当日 00:00, 次日 00:00)` 半开区间构造条件，禁止在列上调用 `date()`。
- [ ] 明确 `eq/ne/gt/gte/lt/lte/between/is_empty/is_not_empty` 各操作符的日期边界和时区口径。
- [ ] 补充 PostgreSQL 方言编译断言，验证所有绑定均为 `DateTime`，SQL 中不出现 `date(`。
- [ ] 增加 `create_time` / `update_time` 等 DateTime 字段的 API 级回归用例。

**验收标准**

- 任何聚合筛选路径均不再生成 `func.date(DateTimeColumn)`。
- 边界测试覆盖当日零点、当日最后一秒、跨月、闰日、空值和非法日期。
- `ruff`、`vulture`、全量 pytest、契约检查、前端三门禁全绿。

**风险**：字段类型与前端操作符映射不一致时可能出现行为变化；必须以现有日期字符串字段的
测试用例作为冻结基线，逐项对照迁移。

### P0-2 并发写入一致性与幂等 ✅（2.20.3）

**问题**

- `ticket_service.assign_ticket_seq` 采用「查询当日最大序号 + 1」，两表都没有可约束的
  `ticket_id` 唯一列，并发创建可能分配到同一工单 ID。
- 报告保存先比较前端提交的 `revision` 再整体写入，没有行锁或带版本条件的原子 UPDATE，
  两个并发请求可能同时通过旧 revision 校验并发生最后写入覆盖。
- 报告导入的「确认入库」没有批次级状态锁或幂等键，同一批次被并发确认时可能重复创建章节、
  漏洞或复测轮次。

**实施项**

- [ ] 为工单序列分配设计数据库级互斥或序列表；至少保证同日、跨 `testing_plans` /
  `nonpen_plans` 的编号分配原子且单调。
- [ ] 为手填工单 ID 增加可校验的数据库唯一策略，不能仅依赖请求前查询；
  联动创建且共享同一工单 ID 的测试计划 / 漏扫基线工单对必须保留为设计内例外。
- [ ] 报告保存改为 `SELECT ... FOR UPDATE` 或带 `revision = :expected` 条件更新；
  冲突统一返回 409，前端保留现有「加载最新 / 继续编辑」流程。
- [ ] 导入确认增加 `pending/parsed -> confirming -> confirmed` 条件状态迁移或 advisory lock；
  重复调用返回既有结果，不重复写入。
- [ ] 为导出、自动导出和通知任务定义幂等键，确保队列重试不产生重复业务副作用。
- [ ] 增加并发测试：同日期双请求创建工单、双端同时保存报告、同批次双确认。

**验收标准**

- 并发测试中不出现非联动关系的重复工单 ID、重复章节、重复漏洞或重复复测轮次。
- 冲突请求返回明确 4xx，不落入 500，不覆盖他人已提交内容。
- 数据库约束、迁移和降级路径通过 `tests/test_migrations.py`。

### P0-3 后台任务生命周期、恢复与健康检查 ✅（2.20.3）

**问题**

- `ExportJob`、`ImportBatch` 只有依赖业务写入的简单状态，没有租约、心跳、尝试次数或恢复扫描。
- worker 在任务执行中崩溃时，记录可能永久停留在 `running` / `parsing`。
- arq 投递失败会降级为 API 进程内任务，但重启会丢失进程内任务。
- `/api/health` 只返回静态 `ok`，不检查 PostgreSQL、Redis、Gotenberg 或队列积压。

**实施项**

- [ ] 为导入与导出任务补齐 `attempts`、`last_heartbeat`、`lease_until`、`next_retry_at`、
  `dead_letter_reason` 等可观测字段，方案需先评估是否合并为统一任务表。
- [ ] 启动时执行一次超时任务回收：超租约任务回到可重试状态或明确标记失败并保留原因。
- [ ] 对可重试错误使用指数退避；对文件损坏、权限错误等永久错误不重试。
- [ ] 保持任务幂等，重试不得重复生成章节、漏洞、复测轮次或报告文件。
- [ ] 增加 `/api/health/live` 与 `/api/health/ready`：数据库为必需依赖；Redis / worker 在队列启用时
  为必需依赖；Gotenberg 为可选能力。ready 返回逐项状态，只有必需依赖失败才返回非 200；
  保留 `/api/health` 兼容现有探针。
- [ ] 日志中增加 `request_id` / `job_id` / `batch_id` 关联字段，便于从界面报错定位后端日志。

**验收标准**

- 强制 kill worker 后，超租约任务在下一轮扫描中可恢复或明确失败。
- Redis 短暂不可用期间，业务请求不被阻塞；恢复后任务可继续投递。
- ready 接口在任一关键依赖不可用时返回非 200，并给出不含敏感信息的依赖状态。
- 故障注入用例覆盖崩溃、重复投递、永久失败和恢复成功四条路径。

### P0-4 列表分页与热点查询性能 ✅（2.20.3）

**问题**

- 漏扫基线工单站内列表与开放 API 在分页前固定取回最多 10000 条，再按 `items` JSON 应用层
  过滤和切片；数据增长后每次请求的数据库读取与应用层内存都会线性放大。
- 漏洞、资产、工单、报告和命令面板检索大量使用 `%keyword%` 模糊匹配，未配置 trigram 或全文索引。
- 缺少大数据量基准，无法判断索引、分页和统计查询的回归。

**实施项**

- [ ] 将「仅可进行」改为 SQL 侧派生条件；优先利用 `items` JSON 固定键和状态白名单构造表达式。
- [ ] 评估给 `nonpen_plans.items` 增加表达式索引或 GIN 索引，并以 `EXPLAIN ANALYZE` 验证命中。
- [ ] 为高频筛选字段补齐索引：漏洞标题 / 状态 / 提交时间、工单接收时间 / 状态 / 部门、
  报告更新时间、审计时间。
- [ ] 评估 `pg_trgm` 或 PostgreSQL 全文检索，替换高成本的前后通配符扫描。
- [ ] 建立可重复的本地性能基准：10 万漏洞、1 万工单、1 万报告三档数据；
  记录查询次数、P50/P95 延迟和慢查询 SQL。

**验收标准**

- 站内与开放 API 的「仅可进行」分页不再读取全量记录。
- 基准数据下列表首屏 P95 达到团队确认的阈值并写入 `docs/RELEASE.md`，阈值需包含数据库与前端等待。
- `EXPLAIN ANALYZE` 证明新增索引被实际使用，且迁移可安全回退。

### P0-5 报告编辑防丢稿与离页保护 ✅（2.20.3）

**问题**

- 报告编辑器采用 3 秒防抖自动保存，但用户可能在保存计时器触发前离开、刷新、退出登录或关闭标签页。
- 当前报告页没有 `onBeforeRouteLeave` / `beforeunload` 保护，也没有统一的「保存中 / 保存失败 /
  待保存」状态。

**实施项**

- [ ] 抽取报告自动保存状态机：`saved / dirty / saving / failed / conflict`。
- [ ] 路由离开前：无修改直接放行；有修改则先尝试一次保存，失败后弹出「继续保存 / 放弃修改 / 留在当前页」。
- [ ] 浏览器 `beforeunload` 仅在确有未保存或保存失败内容时触发原生确认。
- [ ] 保存失败保留本地输入，展示重试入口；409 冲突不得静默覆盖。
- [ ] 退出登录、切换账号和关闭标签页纳入同一保护逻辑。

**验收标准**

- Vitest 覆盖状态机与三类离页分支。
- Playwright 增加「编辑后 3 秒内离开」「保存失败后重试」「409 冲突」三条链路，控制台 0 error。
- 任何导航路径都不会在无提示的情况下丢失未保存报告内容。

## 五、P1：业务闭环与运营能力

### P1-1 F1 SLA 修复时限

**目标**：按漏洞等级和业务规则计算修复截止时间，形成「到期前提醒、逾期告警、逾期统计、
整改督办」闭环。

**建议范围**

- [ ] SLA 策略配置：等级、默认时限、工作日 / 自然日、暂停状态、是否允许延期。
- [ ] 漏洞新增或等级变化时计算 `due_at`；状态进入已修复 / 已忽略时停止计时。
- [ ] 延期操作记录原到期时间、新到期时间、原因、审批人，不允许无痕改期。
- [ ] 漏洞列表、详情、工单抽屉、看板和开放 API 增加剩余时间 / 逾期状态。
- [ ] 到期前提醒和逾期升级接入通知渠道；投递记录可查询。
- [ ] 新增逾期率、平均修复时长、按部门 / 等级 / 来源的 SLA 统计。

**验收标准**

- 截止时间按 UTC+8 业务日计算，覆盖周末、跨月、闰日和节假日配置（若首期不支持节假日需显式标明）。
- 同一次漏洞状态变化只产生一次应发提醒；重试不重复通知。
- 列表、看板、导出、开放 API 使用同一 SLA 判定函数。
- 策略变更默认只影响未来新漏洞；历史批量重算必须显式执行并留审计记录。

**依赖**：P0-1 时间口径、P0-3 通知可靠性、P1-2 站内通知。

### P1-2 个人待办工作台与站内通知中心

**背景**：后端已有 `messages` 表、`/messages` 与 `/messages/read`，但前端没有消息入口；
目前只在漏洞流转和「无漏洞结项」场景写入站内信，无法覆盖认领、复测、报告、SLA 等完整待办。

**实施项**

- [ ] 在顶栏加入通知铃铛、未读徽标、最近消息下拉和完整消息页。
- [ ] 支持按用户查看、单条已读、批量已读、按类型筛选和跳转到对应漏洞 / 工单 / 报告。
- [ ] 定义个人待办聚合：待认领、我提交的漏洞、待复测、待确认导入、SLA 临期 / 逾期。
- [ ] 所有事件通过统一 `create_message()` 服务写入，禁止各路由直接拼装 `Message`。
- [ ] 增加消息保留期和已读消息清理策略，避免无界增长。

**验收标准**

- 刷新页面后未读数与服务端一致；多标签页阅读状态最终一致。
- 消息深链在权限不足时不泄露对象内容，并跳转到明确的无权限页。
- 消息生成失败不影响主业务事务，但必须记录告警。

### P1-3 外部通知投递可观测与失败恢复

**实施项**

- [ ] 建立通知投递记录：渠道、事件、目标摘要、请求时间、状态码、尝试次数、最后错误。
- [ ] 外部通知失败按可重试错误退避重试，超过上限进入死信状态并在通知渠道页可见。
- [ ] 增加「测试发送」结果回执，不再只返回「已入队」。
- [ ] 对 webhook、SMTP、DNS、TLS 超时分别给出可操作错误，不泄露密钥或内网地址。
- [ ] 支持按渠道暂停、恢复和重放单条失败通知。

**验收标准**

- 任一通知均有可查询的最终状态；进程重启不丢失待重试记录。
- SSRF 校验、重定向禁用、内网 allowlist 逻辑不回退。
- 系统管理页可按渠道、事件、状态、时间筛选投递记录。

### P1-4 报告模板中心

**目标**：把当前环境变量指定的单一 Word 模板升级为可在界面维护、预览、版本化和回滚的模板中心。

**实施项**

- [ ] 定义模板元数据：名称、适用报告类型、版本、启用状态、创建人、更新时间。
- [ ] 支持上传 `.docx`、字段占位符校验、模板预览和示例数据试生成；
  上传必须经过 `core/storage.py`、`core/archive.py` 的文件安全与解压配额守卫。
- [ ] 默认模板回退到现有包内 `report_template.docx`，不存在可用模板时系统仍可导出。
- [ ] 导出记录保存使用的模板 ID 与版本，历史报告可追溯。
- [ ] 模板替换必须经过显式发布，禁止直接覆盖正在使用的版本。

**验收标准**

- 模板占位符缺失时阻止发布并给出字段清单。
- 模板发布、停用、回滚均记入审计日志。
- DOCX 与 PDF 导出使用同一模板版本，目录域提示行为不变。

### P1-5 导入与数据治理增强

**实施项**

- [ ] 导入失败批次支持只重试失败记录，成功后保留原批次审计链。
- [ ] 增加重复漏洞候选视图：标题、URL、等级、关联工单和相似度并列展示，支持合并或保留为独立记录。
- [ ] 记录每条解析字段的来源、修正前后值和修正人，形成可追溯数据链。

**验收标准**

## 六、P2：规模化与平台化

### P2-1 部门级 / 多租户数据隔离

- 引入明确的 `scope` 模型，禁止仅在路由层用可选筛选模拟数据权限。
- 权限同时覆盖列表、详情、导出、附件、搜索、审计和开放 API。
- 若模型或既有数据归属发生不兼容变化，按 SemVer 升主版本。
- 验收必须包含越权读取、越权导出、跨部门猜测 ID 和 PAT 作用域测试。

### P2-2 漏洞自动验证与 PoC 插件

- 定义外部验证器接口：输入漏洞结构化字段，输出验证状态、证据、执行时间和错误。
- 插件运行必须隔离网络、文件系统和超时，遵守 `core/outbound.py` 的出站策略。
- 结果只作为辅助证据，不直接覆盖漏洞人工状态。
- 首期建议只接入受控内部插件，开放第三方插件前完成威胁建模。

### P2-3 资产测绘工具联动

- 建立资产同步批次、来源标识和冲突合并策略，禁止自动覆盖人工维护字段。
- 新增 / 下线 / 变更资产形成生命周期事件，供漏洞归属和 SLA 使用。
- 同步失败可重试，保留来源系统 ID 与最近同步时间。

### P2-4 全文检索与数据分析

- 对漏洞、资产、工单、报告建立 PostgreSQL 全文索引或独立检索索引，逐步替换 `%keyword%`。
- 命令面板支持字段级过滤、权限过滤、最近访问和结果高亮。
- 保留数据库为唯一事实源，不引入第二个业务数据库。

### P2-5 备份恢复演练与可观测性

- 每季度至少一次从生产备份恢复到临时环境，验证表数、关键计数、迁移版本与文件完整性。
- 定义 RPO / RTO 目标并记录在 `docs/DEPLOY.md`。
- 增加数据库连接池、慢查询、Redis、worker 队列积压、Gotenberg、磁盘和备份成功率的监控指标。
- 告警必须包含可执行处置建议，禁止只报告“失败”。

### P2-6 移动端与响应式降级

- 优先保证查看、认领、漏洞状态流转、复测填写和通知处理。
- 复杂报告编辑、模板管理和批量导入可继续保留桌面端。
- 以真实设备视口验证表格、抽屉、筛选器和富文本工具栏，不以单纯缩放作为适配。

## 九、单项完成定义（Definition of Done）

任何 ROADMAP 条目只有同时满足以下条件才可移出当前批次：

1. 功能范围与旧行为兼容性已明确，破坏性变化已按 SemVer 处理。
2. 模型变化配套 Alembic 迁移、降级验证与 `DEPRECATED_COLUMNS` 登记。
3. 新增或修改的时区、状态机、统计、复测、权限口径已在实现处保持单源。
4. 后端补充领域测试；涉及 API 契约时更新对应 `tests/api/test_api_<领域>.py`。
5. 前端补充 composable / 组件测试；涉及交互时通过受影响页面浏览器冒烟。
6. `ruff`、`vulture`、全量 pytest、契约检查、`pnpm typecheck`、`pnpm test`、`pnpm run build` 全绿。
7. 发布前运行接口探针；涉及前后端联调时运行 E2E 黄金链路。
8. 用户可见变化更新 `docs/USER_GUIDE.md`，运维变化更新 `docs/DEPLOY.md`，
   脚本变化更新 `docs/SCRIPTS.md`，开放 API 变化更新 `docs/OPEN_API_GUIDE.md`。
9. 发布时更新 `docs/RELEASE.md`、`APP_VERSION`、`frontend/package.json` 并打注解标签。
10. 完成后从本文件当前批次移入「已完成归档」，版本号与回归证据写入 `RELEASE.md`。

## 十二、维护约定

1. 新增条目必须先说明「解决什么真实问题」，不接受仅以技术名词包装的条目。
2. 条目完成并发布后，必须从当前批次移入「已完成归档」，同时在 `docs/RELEASE.md` 留下版本与证据。
3. 若某项连续两个迭代未进入实施，应重新评估优先级；不得只保留标题。
4. 若计划改变既有统计周期、复测三态、漏洞来源、工单状态机或安全边界，必须在条目中写明旧口径、
   新口径、迁移方案和回滚方案。
5. 本文档不记录临时讨论结论；稳定规则进入 `AGENTS.md`，操作流程进入相应长期文档。
