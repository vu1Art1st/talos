## 一、规划原则与当前结论

### 1.1 规划原则

1. **先正确，再扩展**：数据正确性、并发一致性、任务可恢复性优先于新增业务页面。
2. **复用现有单源**：继续统一使用 `app/core/filters.py`、`plan_query`、`plan_service`、
   `report_meta`、`/meta` 字典、前端 `client.ts` 与既有 composables，禁止新造平行实现。
3. **业务改动必须可审计、可迁移、可回滚**：涉及模型变更时同步 Alembic 迁移、
   `DEPRECATED_COLUMNS`、备份与恢复验证、`docs/RELEASE.md`。
4. **不承诺具体日期**：按 P0 → P1 → P2 顺序推进，每项达到验收标准后再发布。
5. **保持既定决策**：不引入 CI，不引入 SQLite，不恢复已取消的扫描器接入与定期报表订阅；
   只有触发条件明确成立时才重新评估。

### 1.2 下一阶段结论

当前 Talos 已跨过「主要功能是否可用」阶段，进入「高频业务是否长期可靠、可运营、可扩展」阶段。
下一阶段不应以页面数量为目标，建议按以下顺序推进：

1. **P0：可靠性加固**：修复已识别的日期筛选隐患、并发写入竞态、后台任务卡死和数据量增长后的
   查询退化；补齐报告防丢稿和基础可观测性。
2. **P1：业务闭环增强**：落地 SLA 修复时限、个人待办工作台、站内通知中心、通知投递可追踪、
   报告模板中心与开放 API 成熟化。
3. **P2：规模化与平台化**：先落地部门级数据权限与可验证的灾备 / 可观测能力，再做权限感知的
   全文检索；资产测绘联动与移动端均不排期，不在 Talos 内建设 PoC 执行器。

在 P2 收尾之后，新增**批次 E：性能与数据访问底座**（数据库查询形状、DOCX/ZIP/lxml 解析链路、
Python 3.14 迁移准备）。该批次已于 2026-09-30 立项规划但**未启动**，详见第六节；只有项目负责人
显式指示后才进入实施，避免与 P2 收尾争用回归窗口。

## 二、现状基线

### 2.1 架构与代码组织

| 层 | 现状 |
|---|---|
| 接入层 | FastAPI，统一 `/api/v1` 前缀；OpenAPI 当前约 115 个路径、158 个操作；PAT 与 JWT 分工明确 |
| 后端核心 | `app/core` 承载配置、认证、分页、筛选、限流、文件安全、出站安全、时间与 Excel 工具 |
| 领域层 | `app/models`、`app/schemas`、`app/services` 按资产 / 漏洞 / 报告 / 导入 / 专项 / 系统分域 |
| 数据层 | PostgreSQL 16 单栈；SQLAlchemy 2.0 async；Alembic 是唯一 schema 演进路径 |
| 异步层 | arq + Redis；Redis 不可用时 API 可降级为进程内任务；2.20.3 起补齐租约 / 心跳 / 重试退避 / 死信与启动回收（`services/task_lifecycle.py`） |
| 前端 | Vue 3 + TS + Pinia；`views` 负责页面，`components` 负责交互，`composables` 负责通用行为 |
| 文档处理 | python-docx 解析、docxtpl/html4docx 生成 DOCX、File Viewer 浏览器预览与打印；导入与导出共用 `report_meta` |
| 部署 | Docker Compose：api / worker / frontend / postgres / redis；备份、恢复、升级均有脚本 |

**组织评价**：分层边界清晰，跨模块共享实现已经大量下沉到 services、core 和 composables。当前主要
问题不是缺少架构层次，而是若干跨接口口径仍需继续收敛，异步任务和并发写入缺少数据库层面的
最终保障。

## 五、P2：当前实施批次

> **当前范围**：实施 P2-1、P2-4、P2-5。P2-2 不引入，P2-3、P2-6 不排期；暂停、取消与重启条件统一见第十节。
> **执行结论**：P2-1 提供统一数据边界，P2-4 依赖该边界实现权限感知检索，P2-5 与两者独立并行。
> 当前实现已完成，剩余工作主要是性能基准、恢复演练和通知投递权限快照等验收证据，不再扩张范围。

### 5.1 状态、顺序与依赖

| 顺序 | 条目 | 状态 | 依赖 | 关闭条件 |
|---|---|---|---|---|
| 1 | P2-1 部门级数据隔离 | 已实现，收尾中 | 现有用户 / 组织模型、P1-7 部门统计口径 | 通知 / 投递任务补齐 scope 快照与发送前复核；全量权限矩阵持续回归 |

**执行顺序**

1. P2-1 是硬前置：没有统一 scope，搜索结果、导出、缓存和开放 API 都可能出现越权或口径分裂。
2. P2-4 在 P2-1 之后实施；搜索、命令面板、分组计数和开放 API 共用统一查询语义。
3. P2-5 与 P2-1 并行推进，不依赖业务数据模型，但必须在发布前完成恢复演练证据。
4. P2-2、P2-3、P2-6 不进入当前批次，不为未确认需求预留生产接口或后台任务。

### 5.2 P2-1 部门级数据隔离

**状态（2026-09-27）**：核心实现已落地；全量 pytest `362 passed / 1 skipped`、22/22 接口探针、
前端三门禁和契约检查通过。通知 / 投递任务的跨任务权限快照仍需补齐。

**目标**：把“部门视图”从一个可选筛选参数提升为统一的数据权限边界，覆盖列表、详情、统计、
导出、附件、搜索、消息、审计、缓存、后台任务和开放 API。

**已交付**

- 复用 `groups` / `group_users` 作为组织身份；一个用户可属于多个组织。
- 新增 `roles.data_scope`，取值为 `all` / `department` / `own` / `none`；`*` 角色始终为 `all`，
  无明确范围时 fail-closed。
- 新增统一资源归属解析和 SQLAlchemy 查询注入，见 `core/data_scope.py`；资产使用 `group_id`，
  漏洞由资产 / 工单 / 提交人推导，报告继承工单或创建人。
- 列表、详情、统计、导出、图片引用、消息、审计、开放 API 和统计缓存均已接入统一 scope。
- 导出 worker 按发起账号重新校验报告权限，权限撤销后任务进入死信。
- 管理端支持角色数据范围和用户组织归属配置；迁移为 `roles.data_scope` 与 `group_users` 查询索引。
- 新增 API 越权矩阵测试，覆盖列表、详情、搜索、隐藏图片和猜测 ID。

**剩余收尾**

- [ ] 通知 / 投递任务保存 scope 快照，并在发送前复核；权限撤销后不得继续投递敏感内容。
- [ ] 在发布前重跑权限矩阵，确认缓存、开放 API 游标与后台任务重放仍遵守同一 scope。

**边界**：不引入物理多租户、分库分 schema 或按租户分实例；组织与成员目录作为基础引用数据，
不按部门业务数据隐藏。

### 5.3 P2-4 权限感知检索

**状态（2026-09-27）**：搜索 API、命令面板过滤 / 最近访问 / 高亮已落地；API 搜索探针、全量 pytest、
前端单测和构建通过。10 万级性能与索引留档仍待完成。

**目标**：用 PostgreSQL 完成跨漏洞、资产、业务工单和报告的统一搜索，不引入第二业务数据库。

**已交付**

- 搜索字段覆盖漏洞标题 / 影响 URL、资产名称 / 子系统 / 部门 / URL、工单名称 / 系统 / 部门、
  报告标题 / 项目名 / 章节标题 / 正文。
- 排名规则固定为“精确标题 > 标题前缀 > 标题包含 > 正文 / URL 命中”，并使用稳定 ID 兜底。
- API 支持实体类型过滤、结果摘要，并自动应用 P2-1 scope。
- 命令面板支持类型切换、最近访问、安全高亮和无结果引导。
- `benchmark_lists.py` 与 `enable_trgm_indexes.py` 已扩展到新检索字段。

**剩余收尾**

- [ ] 在 10 万漏洞、1 万资产、1 万渗透工单、5 千漏扫工单、1 万报告上执行 P95 基准。
- [ ] 为代表性中文词、URL 和跨实体查询留存 `EXPLAIN ANALYZE`，确认 trigram / B-tree 命中。

**验收门槛**：单实体搜索 DB 侧 P95 ≤ 50 ms，命令面板聚合接口端到端 P95 ≤ 300 ms；
搜索结果、分组计数和最近访问不得泄露不可见对象。

### 5.4 P2-5 备份恢复与可观测性

**状态（2026-09-27）**：指标接口、RPO / RTO 参考目标、告警清单和恢复演练脚本已落地；

**目标**：把“备份文件存在”提升为“可恢复到已验证状态，且异常在业务受影响前可见”。

### 6.2 不可协商的落地原则

1. **等价性优先**：替换类改动先做影子实现，python-docx 保留为 oracle 与 fallback，不删除依赖。
2. **只换数据访问层**：`parse_docx` / `parse_report_docx` 的标签匹配、等级映射、汇总表配对与 HTML
   拼接逻辑保持单源，不重写。
3. **独立可回滚**：一项一 PR、一项一开关或独立迁移，禁止合并为一次大改。
4. **不做顺手改进**：如“补回超链接文字”“支持 VML 图片”属行为变更，必须另立专项评审。
5. **安全边界不放松**：解析器保持 `resolve_entities=False` / `no_network=True` / `load_dtd=False`

### 6.7 E-5 Python 3.14 升级（规划，时机另行指示）

**事实前提**：Python 3.12 **未 EOL**。3.12 已于 2025-04 结束常规 bugfix，进入 security-only，
安全支持至 2028-10（PEP 664）。故升级不是安全紧迫动作，定位为长周期维护与生态对齐。

| 3.14 变化 | 机制 | 对 Talos 的收益 | 判断 |
|---|---|---|---|
| 新解释器循环 | 相对 3.13 约 3~5%，个别基准更高 | 纯 Python 执行变快 | 收益有限，端到端无感 |
| PEP 744 实验性 JIT | 官方镜像默认不启用 | CPU 密集场景少量加速 | 不适用 |
| PEP 779 自由线程 | 仅 `3.14t` 构建 | 多核并行计算 | 不适用：async 单线程 + DB 瓶颈，生态与内存风险高 |
| PEP 769 增量 GC | 回收粒度更细 | 降低长驻进程 GC 卡顿 | 边际价值：尾延迟略改善 |
| PEP 649/749 延迟注解 | 注解惰性求值 | 加快导入 / 冷启动，略降内存 | 边际收益；需回归 SQLAlchemy / Pydantic 注解内省 |
| `compression.zstd` | 标准库 zstd | 备份 / 日志压缩更快 | 小额收益 |
| PEP 768 远程调试接口 | 可附加调试器 | 非性能 | 运维便利 |

**前置核查（决定能否启动）**

- [ ] `asyncpg` 是否已发布含 CPython 3.14 wheel 的版本（首要阻塞项，C 扩展）

- [x] `bcrypt<4.1` 钉死版本已移除，当前使用 `bcrypt>=5.0.0`

**升级范围（改动点）**：`backend/Dockerfile`、`backend/ruff.toml`（`target-version`）、
`dev.ps1` / `dev.sh`（`--python 3.12`）、`AGENTS.md`、`README.md` / `README_EN.md`、

### 10.3 公网 IPv4 HTTPS + SafeLine WAF（暂缓）

> **状态（2026-10-05）**：已形成可实施方案但暂缓启动，不承诺版本和日期，不加入批次 C / D / E。
> 当前系统继续采用白名单访问方案，安全边界和访问控制满足现状；仅在 10.2 的重启条件出现时重新评估。

**目标链路**：`Internet -> Caddy -> SafeLine -> Talos frontend -> API`。

**已固化结论**

- Caddy 固定 `2.11.7-alpine`，独占公网 80 / 443，使用 Let's Encrypt `shortlived` IP 证书。
- 443 需要访问白名单时，Caddy 必须强制使用 HTTP-01（`disable_tlsalpn_challenge`）；80 保持公网可达，仅承担 ACME challenge 和 HTTPS 跳转。
- 443 可按固定办公网、VPN 或可信出口 CIDR 设置网络层白名单；若不满足固定出口条件，则保留公网可达并在 SafeLine 使用应用层白名单。
- SafeLine 固定 `9.4.2`，只做 HTTP WAF，不负责 IP 证书申请或 TLS 终止；站点监听 `127.0.0.1:8081`，上游为 `http://127.0.0.1:27012`，源 IP 从 `X-Forwarded-For` 获取。
- SafeLine 管理控制台 9443 仅允许运维网段访问；8081 和 Talos 前端 27012 不向公网开放。
- Talos 仅在 edge / 生产环境启用 `VP_TRUSTED_PROXY_HOPS=3`、`VP_COOKIE_SECURE=true`、`VP_PUBLIC_BASE_URL=https://<IPv4>`；本地开发继续使用 `TRUSTED_PROXY_HOPS=1`，避免本地路径和来源 IP 失真。
- Caddy、SafeLine 作为独立 edge 栈，不成为 Talos 基础 Compose、pytest、Vitest 或 E2E 的硬依赖。

**验证边界**

- 本地可完成基础镜像构建、后端 / 前端门禁、E2E、Caddy 配置校验和 SafeLine 基础冒烟。
- 公网 IP 证书、运营商 / 防火墙白名单、真实客户端 IP 和 6 天证书续期必须到公网 staging 或生产环境验证，不能由本地私网环境替代。

**实施前前置**

- 完成安全评审，确认固定公网 IPv4 和 80 / 443 可达性。
- 确认 443 白名单 CIDR、运维管理网段、回滚路径和 edge 证书过期告警设计。
