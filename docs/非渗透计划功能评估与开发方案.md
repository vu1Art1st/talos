## 一、核心结论（TL;DR）

| 维度 | 结论 |
|------|------|
| 技术可行性 | **高**。与现有「测试计划」模块（`TestingPlan`）技术栈、代码风格完全同构，可复用全部基础设施（权限、分页、迁移、审计）。 |

## 二、需求在现有架构中的技术可行性

### 2.1 与现有系统的高度同构性

| 需求点 | 现有对应物 | 复用情况 |
|--------|-----------|---------|
| 独立菜单 / 路由 / 列表页 | `TestingPlanList.vue` + `MainLayout.vue` + `router/index.ts` | 直接复制同构页面骨架 |
| 新增/编辑弹窗（760px 两列 grid） | `TestingPlanList.vue` 内 `el-dialog` | 直接复用表单布局与控件 |
| 统计面板（5 卡片） | 测试计划 `stats` 接口 + 数字卡片 | 复用 `GET .../stats` 模式 |
| 流程抽屉（测试项状态流转） | `PlanWorkflowDrawer.vue` 抽屉模式 | 新建 `NonpenPlanWorkflowDrawer.vue`，交互逻辑参照演示 `app.js` |
| 状态机 + 字典 | `constants.py` 的 `PlanStatus` / `TESTING_PLAN_STATUS` | 新增独立常量，不动现有 |
| 权限 | `special:manage` | 沿用（非渗透计划属专项管理范畴） |
| 分页 / 搜索 / 排序 | `core/query.py` 的 `paginate` / `apply_sort` | 直接复用 |
| SQLite/PostgreSQL 双轨迁移 | `_migrate_lightweight` + Alembic | 按既有模式补迁移 |
| `assets` 关联（多选，JSON 存 ID 数组） | `TestingPlan.asset_ids`（JSON） | 完全同构 |
| 柔和标签 / 明暗双主题 | `utils/colors.ts` + `style.css` 设计令牌 | 演示中的色板与现有 `colors.ts` 一致，直接沿用 |

结论：**本需求不引入任何新技术栈、新第三方依赖**，是现有「测试计划」模块的一次横向复制 + 定向改造，可行性高。

### 2.2 三个真正的技术难点

1. **工单ID跨模块共享序列**（需求 2.10）——影响现有 `TestingPlan` 的工单ID生成逻辑，是唯一涉及存量数据与存量代码改造的点，详见「五、关键技术点」。
2. **互相级联删除**（需求 2.11）——需同时改测试计划与非渗透计划两端的删除接口。
3. **「仅可进行」筛选**——`items` 以 JSON 存，SQL 层无法直接过滤，需应用层过滤（影响分页语义），详见「六、风险」。

## 五、关键技术点：跨模块共享工单ID序列（★）

### 5.1 现状

- `TestingPlan.ticket_seq` 为表内字段，`_assign_ticket_seq`（`special.py`）只查询 `testing_plans` 表计算「当日最大编号+1」。
- `_check_ticket_id_unique` 只校验 `testing_plans` 表内的手动值/自动值唯一。
- `TestingPlan.ticket_id` 为派生 property：手动指定优先，否则 `receive_time`(YYYY-MM-DD) → `YYYYMMDD-N`。

### 5.2 目标行为（需求 2.10）

| 录入动作 | 消耗序号 |
|---------|---------|
| 纯渗透测试计划 | 1 个 |
| 混合工单（勾选创建非渗透） | **测试计划与非渗透计划共用 1 个** |
| 纯非渗透计划 | 1 个 |

即：同一 `receive_time` 日期内，两表合计序号连续、全局唯一。

### 5.3 改造方案（推荐：不新增序号表）

1. `_assign_ticket_seq` 泛化为 `_assign_ticket_seq(session, row)`，改为**同时扫描 `testing_plans` 与 `nonpen_plans` 两表**的 `ticket_seq` 与 `ticket_id_manual`（解析 `YYYYMMDD-N` 且日期匹配当日）取最大 +1。逻辑与现有函数完全一致，只是 FROM 范围扩到两表。
   - 混合工单场景：**测试计划先分配 seq=N，非渗透计划直接复用同一 N**（不重新分配）。在 `create_testing_plan` 接口内，当 `create_nonpen=true` 时，先 `_assign_ticket_seq(plan)`，创建非渗透计划时手动把 `ticket_seq` 设为 `plan.ticket_seq`、`receive_time` 设为与计划一致。
   - 纯非渗透：非渗透创建接口单独调用 `_assign_ticket_seq`。
2. `_check_ticket_id_unique` 泛化为两表校验（测试计划保存时查两表，非渗透保存时同样查两表，排除自身）。
3. 两端接口的事务：混合创建时，`create_testing_plan` 内用同一个 session 同时 add 两条记录，`commit` 前做一次 `flush` 保证同事务。

**为什么不做 `ticket_numbering` 表**：
- 现有 `ticket_seq` 字段已承载存量数据，测试计划页的筛选（`_ticket_id_filter_expr`）、导入、导出都基于该字段语义；换表意味着存量 `ticket_seq` 回填 + 两套序号源并存，回归面大。
- 两表扫描方案改动集中在 `special.py` 两个函数内，存量数据零迁移、行为零变化（未联动时行为与现在完全一致）。
- 并发场景（两人同时提交）：现有实现本就有「读-算-写」非原子窗口，本次不放大风险；如后续并发要求高，可在 `ticket_seq` 上加两表唯一索引兜底（混合场景同一 seq 在两表各一条，不冲突；纯渗透/纯非渗透同 seq 跨表各一条，同样不冲突——唯一性天然成立，因为序号是「跨表共享」而非「表内唯一」）。此点可留到实现时评估。

### 5.4 手动指定工单ID

沿用现有语义：`ticket_id_manual` 非空则优先，不触发自动分配；唯一性校验对两表生效。混合场景下，非渗透计划沿用测试计划的手动 ID（把同一 `ticket_id_manual` 写入非渗透记录）。

## 六、后端 API 设计

> 建议新建 `app/api/v1/nonpen.py`（权限沿用 `special:manage`，与测试计划一致），并在 `api/v1/__init__.py` 注册；不并入 `special.py`（其已 1277 行，避免继续膨胀）。

### 6.1 非渗透计划 CRUD

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/nonpen-plans` | 分页列表。参数：`search`（名称/工单ID/系统/部门）、`actionable`（true=仅可进行）、`page/size`。响应含 `ticket_id`、`items`、`actionable` 布尔、`linked` 布尔 |
| POST | `/api/v1/nonpen-plans` | 新增纯非渗透计划。分配工单ID（`_assign_ticket_seq`），勾选测试项置 `not_started`，未勾选置 `ignored` |
| GET | `/api/v1/nonpen-plans/{id}` | 详情（供流程抽屉） |
| PUT | `/api/v1/nonpen-plans/{id}` | 编辑基本信息。**联动记录禁止改 `testing_plan_id`**；校验工单ID两表唯一 |
| DELETE | `/api/v1/nonpen-plans/{id}` | 删除。若 `testing_plan_id` 非空 → 级联删除对应测试计划（含其下漏洞/报告解除关联，复用现有 `delete_testing_plan` 逻辑） |
| GET | `/api/v1/nonpen-plans/stats` | 统计：`total` / `retest_done` / `baseline_times` / `host_times` / `web_times`（口径见需求 2.8） |

> 注意：`/stats` 与 `/nonpen-plans/{id}` 的路由顺序——`/stats` 需注册在 `/{id}` 之前（现有 `special.py` 已有相同注释提醒）。

### 6.2 测试项状态流转（收敛为 2 个接口）

对比需求附录的 9 个 action 接口，建议收敛为通用接口 + 白名单校验：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/nonpen-plans/{id}/items/{key}/transition` | body：`{ "action": "start" \| "done" \| "direct_done" \| "start_retest" \| "pass" \| "fail" }`，后端按 `NONPEN_ITEM_ACTIONS` 校验并更新 status / first_times / retest_times |
| POST | `/api/v1/nonpen-plans/{id}/items/{key}/ignore` | body：`{ "ignored": true \| false }`（忽略/取消忽略） |

计数规则（对齐演示 `app.js`）：
- `start`：`not_started → testing`，`first_times += 1`
- `done`：`testing → wait_retest`
- `direct_done`：`testing → retest_done`（仅此状态可用）
- `start_retest`：`wait_retest → retesting`，`retest_times += 1`
- `pass`：`retesting → retest_done`
- `fail`：`retesting → wait_retest`（次数已计，不回退）
- `ignore`：任意状态 → `ignored`；`unignore`：`ignored → not_started`，次数清零或保留？——**建议保留清零**（演示 `setIgnored` 不置零次数，但需求 2.4 说「忽略后可取消忽略（回到未开始）」。需与用户确认次数是否清零；默认实现参照演示：取消忽略回 `not_started`，次数保留，仅状态变化）。

### 6.3 测试计划接口联动（改造现有）

- `TestingPlanIn` 增加：`create_nonpen: bool = False`、`nonpen_test_items: list[str] = []`（勾选测试项，默认空）。
- `create_testing_plan`（`special.py`）改造：
  - 事务内：创建测试计划 → `_assign_ticket_seq` → 若 `create_nonpen=true`：
    - 校验 `nonpen_test_items` 非空（为空则 400「请至少选择一个测试项」）且都在 `NONPEN_ITEMS` 内；
    - 创建 `NonpenPlan`，`ticket_seq` / `ticket_id_manual` / `receive_time` **沿用测试计划**，`testing_plan_id` 指向新计划，勾选项 `not_started`、未勾选 `ignored`。
  - 复用 `_check_ticket_id_unique`（两表版本）。
- `update_testing_plan`：编辑时不联动同步非渗透计划字段（**默认行为，需用户确认**，见「八、待澄清」）；`create_nonpen` 变更不回写已有非渗透记录。
- `delete_testing_plan`：删除前查出 `nonpen_plans` 中 `testing_plan_id = row_id` 的记录一并删除（同事务）。

### 6.4 「仅可进行」筛选实现

`GET /nonpen-plans?actionable=true`：取回全部记录后在**应用层**过滤（`items` 中任一非忽略项处于 `not_started/testing/retesting`）。数据量评估：非渗透计划属工单级，量级与测试计划相当（千级以内），先全量过滤再分页完全可接受；若未来量大，再考虑 SQLite `json_extract` / PostgreSQL JSONB 表达式索引，此点在方案中预留但不先行实现。

## 十一、上线后整改记录（2026-08-10）

### 11.1 Bug 一：非渗透计划流程抽屉空白

**根因**：`NonpenPlanWorkflowDrawer.vue` 组件在父页面**常驻渲染**，仅在组件首次 `onMounted` 时调用一次 `load()`；此时 `planId` 为 `null`（抽屉尚未打开），`load()` 直接 return。之后每次打开抽屉 `planId` 已赋值，但没有监听 `planId/visible` 变化，`plan` 恒为 `null` → 抽屉内容空白。

**修复**：参照 `PlanWorkflowDrawer.vue` 的既有模式，改为 `watch(() => [props.visible, props.planId], ...)`，打开时重置并 `await load()`。

### 11.2 Bug 二：新建工单 / 联动工单未生成工单ID

**根因**：工单ID = 手动指定值 或 `receive_time`（需求接收日期）+ `ticket_seq` 派生。当「需求接收日期」与「手动工单ID」**均为空**时：
- 直接新建非渗透计划：`assign_ticket_seq` 因 `receive_time` 为空直接 return，`ticket_seq` 保持 0 → `ticket_id=''`；
- 测试计划勾选「创建非渗透」联动：测试计划 `receive_time` 为空则同样不分配序号，联动非渗透复用 `ticket_seq=0` → 双方工单ID均空。

**修复**（前后端双重校验）：
- 后端 `NonpenPlanIn` 增加 `model_validator`：`ticket_id_manual` 与 `receive_time` 至少填其一；
- 后端 `create_testing_plan` 联动分支：`create_nonpen=true` 时若两者皆空则 400 提示；
- 前端 `NonpenPlanList.vue` / `TestingPlanList.vue` 的 `save()` 增加同口径前置校验并弹提示。

**验证**：TestClient 复现确认——带日期正常生成 `20260811-1`；两者皆空返回 422/400 并提示；联动带日期时测试计划与联动非渗透共享同一工单ID（`20260811-3`）。

### 11.3 「测试计划」更名为「渗透测试计划」

- 前端：菜单 / 路由 title / 列表页按钮·空态·弹窗·表头 / 统计卡片 / 导出文件名 / 导入模板文件名 / 漏洞详情·报告·导入·表单面板等全部用户可见文案更新；
- 后端：Excel sheet 名、导出文件名、导入模板文件名、`PLAN_EXCEL_HEADERS` 表头、错误提示（`渗透测试计划不存在` / 认领 / 漏洞权限）更新；
- **兼容性**：路由 `/testing-plans`、API 路径、数据库表名 `testing_plans` 均保持不变，不破坏既有链接、权限与数据；
- 测试：`tests/test_api.py` 的 sheet 名与表头断言同步更新。

### 11.4 共用同一张数据表评估（结论：不建议合并）

| 维度 | 分开两表（现状） | 合并一表（+ kind 字段） |
|------|------------------|------------------------|
| 共享工单ID序列 | 已通过 `ticket_service` 两表扫描解决，实测共享正确 | 天然同表，无需额外逻辑 |
| 字段模型 | 各自精简：测试计划有状态/人天/漏洞/复测轮次，非渗透仅 items | 需容纳两类业务字段，`testing_plans` 已有 25+ 列再叠加非渗透字段，null 大量增加 |
| 状态机 | 测试计划 6 态 + 非渗透 item 6 态，互不干扰 | 需在模型层加 `kind` 分支，状态流转/校验复杂度上升 |
| 联动/级联 | `testing_plan_id` 外键表达清晰 | 同表后需自引用外键表达联动，语义混乱 |
| 迁移成本 | 已建成上线，无存量影响 | 需合并表 + 数据搬迁 + 全量回归，风险高 |
| 职责边界 | 测试计划=渗透（漏洞/报告/人天），非渗透=扫描（独立统计），与「业务独立」需求一致 | 混合表违背需求确认的「非渗透不关联漏洞/报告/人天」隔离 |

**结论**：维持两表 + `ticket_service` 共享序列的方案，当前实现已覆盖合并方案的唯一收益点（共享工单ID），且不引入合并表的字段膨胀、状态机耦合与迁移风险。

### 11.5 统计口径修正：初测复测合计算一次

**问题**：统计卡片「基线 / 主机 / Web 扫描次数」原按「初测次数 + 复测次数」累加。一个测试项完整走完 初测（`first_times=1`）+ 复测（`retest_times=1`）后被计为 2 次，复测多次则更多。

**修正**：`compute_plan_stats` 改为按「初测次数」统计（`first_times`）。初测与复测针对同一测试项，是同一项测试的一次完整执行，合计按一次计；复测多次也不重复计数。由于 `first_times` 每项最多 +1（`reset`/`unignore` 清零后重新 `start` 才再加），该口径等价于「被测试过的测试项计数」。

**验证**（增量断言，TestClient）：
| 场景 | 初测/复测动作 | 扫描次数增量 |
|------|--------------|------------|
| baseline | start→done→start_retest→pass | 1 |
| host | start（仅初测） | 1 |
| web | start→done→start_retest→fail→start_retest→pass（复测 2 次） | 1 |

`total` 增量 3、`retest_done` 增量 2（仅初测未复测完成的计划不计入），全部符合预期。
