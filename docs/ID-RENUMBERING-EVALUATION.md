# 测试计划与导入批次 ID 重排可行性评估

> 评估日期：2026-08-03
> 评估范围：需求七「删除测试计划后重排计划序号、删除导入报告后重排导入报告批次序号」
> 结论：**不重排主键 ID**，推荐以业务序号字段替代（如需连续展示）。

---

## 一、现状

- 测试计划主键 `testing_plans.id` 为数据库自增整数（SQLite / PostgreSQL 通用）。
- 导入批次主键 `import_batches.id` 为数据库自增整数，用于生成批次流水号（`seq`）。
- 删除计划 / 批次后，自增计数器不回退，新纪录的 ID 会跳号（如删除 ID=3 后新增变为 ID=4/5）。

## 二、外键引用关系（重排风险来源）

### 2.1 测试计划 `testing_plans.id` 被以下表引用

| 引用表 | 字段 | 删除策略 | 说明 |
| --- | --- | --- | --- |
| `vulns` | `testing_plan_id` | 可空，API 层置空 | 漏洞归属计划，数量大、持续增长 |
| `reports` | `testing_plan_id` | 可空，API 层置空 | 报告归属计划 |
| `testing_plan_retest_rounds` | `plan_id` | CASCADE | 复测轮次审计记录 |
| `testing_plan_testers` | `testing_plan_id` | CASCADE | 测试人员认领关联 |

### 2.2 导入批次 `import_batches.id` 被以下表引用

| 引用表 | 字段 | 说明 |
| --- | --- | --- |
| `import_records` | `batch_id` | 每批可能数百条漏洞记录 |
| `import_records` | `vul_id` | 入库后关联已创建漏洞（跨表引用） |
| 审计日志 `vul_logs.content` | 文本含 `来源批次 #N` | 非结构化引用，重排后无法批量更新 |

### 2.3 其他引用

- 前端 URL、历史导出 Excel、报告编号、消息通知等均可能硬编码或引用展示用的 ID。
- `ticket_id`（工单ID `YYYYMMDD-N`）虽然独立于主键，但其「当日录入次序」与计划创建顺序强相关，重排主键会打乱次序口径。

## 三、重排主键的风险

1. **级联更新面大且易遗漏**：需同时更新 4 张关联表中的外键值，任一遗漏即产生悬挂引用或脏数据。
2. **SQLite 不支持修改主键**：需 `ALTER TABLE ... RENAME` + 重建表 + 逐表迁移数据，涉及 12+ 张表，事务边界复杂，失败回滚代价高；生产 PostgreSQL 可改但同样需要完整锁表迁移。
3. **破坏审计一致性**：`vul_logs` 中「来源批次 #3」等文本记录、复测轮次来源说明不可批量改写，重排后日志与数据对不上。
4. **违反 ID 唯一性直觉**：历史已导出的 Excel / 报告中的 ID 与新库数据 ID 发生位移，追溯困难。
5. **收益低**：ID 跳号不影响排序、统计、筛选、导出等功能；用户感知的「序号连续」更多是展示层诉求。

## 四、推荐方案（不重排主键）

| 场景 | 方案 | 说明 |
| --- | --- | --- |
| 测试计划 | 主键不变，展示序号由 `plan_seq` 字段承载 | 新增时取 `max(plan_seq)+1`；删除后按当前列表重排该字段（仅更新一行序号列，不动主键与外键）；列表/导出按 `plan_seq` 展示 |
| 导入批次 | 主键不变，批次号沿用现有 `seq` 或 `ImportBatch.seq` | 同上：展示用序号字段重排，`import_records.batch_id` 不涉及 |

实施要点：

- `plan_seq` / `batch_seq` 为普通整数列，无唯一约束（允许短暂重复），重排时在事务内批量更新。
- 重排触发时机：删除计划 / 删除批次后，按 `id` 升序重写序号。
- 与工单ID「当日录入次序」解耦：工单ID 使用 `ticket_seq`（按 `receive_time` 日期计数），不受计划删除影响，保持审计口径稳定。

## 五、结论

**不建议重排自增主键 ID。** 主键被多张业务表外键引用且存在非结构化审计引用，重排风险远高于收益。若需「序号连续递增」的展示效果，请采用第四节的业务序号字段方案，实现成本低、风险可控，且不影响数据引用完整性。
